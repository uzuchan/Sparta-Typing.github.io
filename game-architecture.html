Sparta Typing ゲーム周りブロック図

現状の処理は「入力イベント」「ゲーム状態」「判定」「表示」がかなり近い距離でつながっています。 カタカナ問題は一部直せましたが、かな打ちを正式対応するなら入力方式を独立した層として扱うのが自然です。

Input

useTypingInput

物理キーボードの keydown と mobile hidden input を受け取り、 許可文字だけを onChar に流します。

State

gameStore.onChar

現在の入力文字列を作り、方向に応じて judgeRomajiInput または judgeEnglishInput を呼びます。

Judge

romaji.ts

読みからローマ字候補を生成し、prefix match / completed / kanaProgress を返します。 直接カナ入力もここで同じ結果に正規化しています。

View

WordCard

store の input と inputProgress を使って、 入力済み文字・カーソル・残りヒントを描画します。

Timer

useGameLoop

残り時間・落下演出・タイムアップを管理します。

Question

engine.ts

単語データからゲーム用の question / target / reading / display を構築します。

Result

DB / scoring / mastery

正答時にスコア・習熟度・復習予定・セッション結果へ反映します。

かな打ち対応のおすすめ設計

かな打ちは「ローマ字入力の別パターン」ではなく「入力方式が違うだけで、答えの進捗は同じ」と考えるのが安全です。 そのため、次のような Adapter 層を追加します。

Raw key
keydown / input
→
Input Adapter
romaji / kana / direct
→
Judge
InputAttempt

1. 入力方式を mode 化

  • inputMethod: "romaji" | "kana" | "direct" を持つ
  • ゲーム開始時に既定は romaji
  • 将来 UI で切り替え可能にする

2. Raw key を答え単位に変換

  • ローマ字: k a → か 進捗候補
  • かな打ち: JIS 配列 key → かな文字
  • 直接 IME: 入力済み文字を normalize

3. 表示は attempt を見る

  • rawInput: ユーザーが打ったもの
  • normalizedInput: 判定用
  • progress: 表示用

実装メモ

  • 今の judgeRomajiInput(kana, input) は名前がローマ字寄りなので、 judgeJapaneseInput(reading, attempt) に寄せると責務が明確になります。
  • かな打ちではブラウザの KeyboardEvent.key だけだと OS 配列・JIS/US 配列の差が出やすいです。 安定させるなら「直接かな入力」と「物理かな配列」の対応を分けて扱います。
  • 最初の実装は direct kana 入力を正式機能として磨き、次に JIS かな配列 adapter を追加する順が安全です。
